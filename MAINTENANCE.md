# MAINTENANCE.md — Техническая документация для сопровождения

Этот документ описывает внутреннее устройство каждого компонента проекта, логику его работы и практические рекомендации по сопровождению. В отличие от `ARCHITECTURE.md` (проектные решения и почему они приняты) и `README.md` (как запустить и задеплоить), здесь — подробный разбор "что как работает внутри" и "что делать, если что-то сломалось".

---

## 1. Обзор системы

Бот раз в день (по расписанию из БД) собирает новости по заданным темам из RSS-источников, отправляет их в Anthropic API для фильтрации/сопоставления/форматирования, и присылает готовый дайджест в Telegram — отдельным сообщением на каждую тему.

Поток данных целиком описан в `ARCHITECTURE.md`, раздел 1. Здесь — по каждому файлу отдельно.

---

## 2. Модуль `bot/config.py`

**Назначение:** единая точка загрузки и валидации конфигурации из `.env`.

**Ключевой объект:** `settings` — экземпляр класса `Settings(BaseSettings)`. Поля: `bot_token`, `anthropic_api_key`, `db_path` (с значением по умолчанию `"news_bot.db"`).

**Логика:** при импорте модуля (`from bot.config import settings`) `pydantic-settings` сразу читает `.env` и проверяет наличие всех обязательных полей. Если чего-то не хватает — приложение упадёт **при старте**, с понятной ошибкой, а не в середине работы.

**На что обратить внимание при сопровождении:**
- Любая новая переменная окружения (например, при добавлении нового внешнего сервиса) добавляется как новое поле в класс `Settings` — иначе `pydantic-settings` её просто не увидит.
- `DB_PATH` должен совпадать в трёх местах одновременно: `.env`, том, куда монтируется Docker volume (`/app/data/...`), и путь, который использует `alembic` (см. раздел про миграции ниже) — рассинхронизация этих трёх мест уже становилась причиной реальной ошибки (`no such table`) при первом деплое.

## 3. Модуль `bot/models.py`

**Назначение:** SQLAlchemy-описание всех 6 таблиц БД.

| Класс | Таблица | Ключевые связи |
|---|---|---|
| `User` | `users` | 1:N → `Schedule`, `UserTopic` |
| `Schedule` | `schedules` | N:1 → `User` |
| `Topic` | `topics` | 1:N → `Source`, `UserTopic` |
| `Source` | `sources` | N:1 → `Topic` |
| `UserTopic` | `user_topics` | связующая таблица `User` ↔ `Topic`, хранит `depth_level` |
| `SentArticle` | `sent_articles` | N:1 → `UserTopic`, используется для дедупликации |

**Важно помнить:** `depth_level` (уровень глубины: `summary`/`briefly`) находится в `UserTopic`, а не в `Topic` — это осознанное решение: один и тот же справочник тем может обслуживать разных пользователей с разной глубиной подписки.

**При изменении схемы:** любое изменение полей в этом файле требует новой миграции Alembic (см. раздел 8) — саму таблицу в БД руками менять нельзя, иначе `alembic` и реальная структура БД разойдутся.

## 4. Модуль `bot/db.py`

**Назначение:** подключение к БД и функции для дедупликации.

**Функции:**
- `get_unsent_articles(session, user_topic_id, articles) -> list[Article]` — фильтрует уже отправленные статьи (по `url`), сравнивая **в рамках конкретной связки** пользователь+тема (`user_topic_id`), а не глобально по всей таблице.
- `mark_as_sent(session, user_topic_id, articles) -> None` — записывает переданные статьи как отправленные. **Критично:** вызывать только после успешной отправки сообщения в Telegram — иначе при сбое отправки статьи будут ошибочно помечены как доставленные и больше никогда не появятся в дайджесте.

**Известный подводный камень — `DetachedInstanceError`:** если объект SQLAlchemy (например, `User`) используется **после** `session.close()` или после `session.commit()` в той же сессии — обращение к его полям может вызвать эту ошибку, так как SQLAlchemy "просрочивает" объекты после коммита. **Правило:** любое значение, которое понадобится после закрытия сессии, нужно скопировать в обычную переменную (`chat_id = user.telegram_chat_id`), пока сессия ещё активна.

## 5. Модуль `bot/schemas.py`

**Назначение:** структуры данных, не привязанные к БД — используются для передачи данных между модулями в рамках одного "прогона" (не сохраняются напрямую как таблицы).

- `Article` — одна новость: `title`, `url`, `content`, `published_at`, и автоматически вычисляемый `content_hash` (MD5 от заголовка+текста, используется для дедупликации по смыслу, если понадобится сравнение помимо URL).
- `DigestBlock` — результат обработки одной темы: `topic_name`, `content_text`.

## 6. Модуль `bot/news_fetcher.py`

**Назначение:** получение статей из одного RSS-источника.

**Функция:** `fetch_articles(source: Source) -> list[Article]`.

**Логика:**
1. Скачивает содержимое ленты через `requests.get(..., timeout=10, headers=HEADERS)`.
2. `raise_for_status()` — проверка HTTP-кода ответа.
3. Передаёт скачанные байты в `feedparser.parse(...)`.
4. Формирует список `Article`, используя `.get(поле, "")` для устойчивости к отсутствующим полям в записи.

**Почему именно так, а не `feedparser.parse(url)` напрямую:** без явного `timeout` `feedparser` может "зависнуть" на неотвечающем сервере на неопределённое время — это реально происходило с одним из источников. `HEADERS` с кастомным `User-Agent` нужен, потому что некоторые серверы (например, `consultant.ru`) отклоняют запросы без "браузероподобного" заголовка.

**При добавлении нового источника:** сначала проверьте его вручную (можно временно написать мини-скрипт, как делалось на этапе разработки) — не все сайты, заявляющие RSS, отдают его стабильно; некоторые требуют специфичных заголовков или блокируют автоматические запросы.

## 7. Модуль `llm_providers/`

**Назначение:** абстракция над LLM-провайдером (паттерн "адаптер") — остальной код не завязан на конкретного провайдера.

- **`base.py`** — абстрактный класс `LLMProvider` с единственным обязательным методом `complete(prompt: str) -> str`.
- **`anthropic_provider.py`** — `AnthropicProvider`, реальная реализация через Anthropic API (модель `claude-sonnet-4-6`, `max_tokens=1024`).
- **`fake_provider.py`** — `FakeProvider`, тестовая заглушка, возвращающая фиксированный текст. **Использовать только для разработки/тестирования**, никогда не оставлять активной в проде.

**При смене провайдера** (например, на локальную модель через Ollama) — нужно создать новый файл (например, `local_ollama_provider.py`) с классом, наследующим `LLMProvider`, реализовать `complete()`, и заменить одну строку в `main.py` (`provider = ...`). Остальной код менять не нужно.

**Известное ограничение:** Anthropic API проверяет географию исходящего IP при каждом запросе, не только при оплате — сервер, с которого идут запросы, должен физически находиться (или маршрутизироваться) через поддерживаемый регион.

## 8. Модуль `bot/ai_processor.py`

**Назначение:** формирование промпта и вызов LLM для одной темы.

**Функция:** `filter_and_format(articles, topic, depth_level, provider) -> DigestBlock`.

**Логика промпта (`_build_prompt`):**
1. Склеивает все статьи в текст.
2. Подставляет инструкцию по глубине (`summary` / `briefly`) — словарь `depth_instruction`.
3. **Явно требует ответ на русском языке**, независимо от языка исходных статей — без этой инструкции модель может ответить на языке источника.
4. Просит модель написать "значимых новостей не найдено", если после фильтрации ничего не осталось — защита от "додумывания" несуществующих новостей.

**При изменении требований к формату дайджеста** (например, добавление ссылок на источники в каждой строке) — правки вносятся именно в текст промпта внутри `_build_prompt`, а не в код обработки ответа: сам ответ модели используется как есть, без пост-обработки.

## 9. Модуль `bot/digest_builder.py`

**Назначение:** форматирование готового блока темы и разбиение длинных сообщений под лимит Telegram.

- `format_block(block) -> str` — оборачивает тему в `📌 <b>Название</b>\nТекст`.
- `split_into_messages(text, max_len=4000) -> list[str]` — режет текст на части не длиннее `max_len`, по границам строк (`\n`), а не посередине текста.

**Почему `max_len=4000`, а не `4096`:** запас на случай, если HTML-разметка (`<b>...</b>`) добавит символы сверх видимого текста. Ограничение в 4096 символов на сообщение — это ограничение самого Telegram, обходить его невозможно, только разбивать на несколько сообщений (что уже сделано).

**Реальный кейс, из-за которого это появилось:** изначально весь дайджест по всем темам собирался в одно сообщение — при большом объёме реального ответа от ИИ это приводило к ошибке `Bad Request: message is too long`. Решение — одно сообщение на тему.

## 10. Модуль `bot/scheduler.py`

**Назначение:** настройка `APScheduler` для срабатывания в заданное время по каждому активному расписанию.

**Функция:** `setup_scheduler(job_func: Callable) -> AsyncIOScheduler`.

**Логика:** читает все активные записи `Schedule` из БД, для каждой создаёт задачу с `CronTrigger(hour, minute, timezone=...)` и уникальным `id=f"schedule_{schedule.id}"`.

**Важно про `id` задачи:** идентификатор строится по `schedule.id` (записи расписания), а не по `user_id` — это позволяет одному пользователю иметь несколько расписаний одновременно (например, утреннюю и вечернюю рассылку) без конфликта идентификаторов. Использование `user_id` в `id` задачи было реальной ошибкой на этапе разработки (`ConflictingIdError`), исправлено на `schedule.id`.

**`job_func`** передаётся снаружи (из `main.py`) через `functools.partial` — сам `scheduler.py` не знает, что именно выполняется по расписанию (реализует паттерн внедрения зависимости), только **когда**.

**При добавлении нового расписания** — используется таблица `schedules` напрямую (через `db.py` или SQL), но **изменения вступят в силу только после перезапуска бота** — `setup_scheduler()` читает расписания один раз при старте, а не отслеживает изменения в БД "на лету". Если понадобится динамическое добавление расписаний без перезапуска — это доработка на будущее (сейчас не реализовано).

## 11. Модуль `bot/handlers.py`

**Назначение:** обработчики команд Telegram.

| Команда | Действие |
|---|---|
| `/start` | Регистрирует пользователя (или находит существующего) |
| `/topics` | Показывает активные темы пользователя и их глубину |
| `/pause` | `is_paused = True` |
| `/resume` | `is_paused = False` |
| (любой другой текст) | echo-ответ (черновая заглушка из раннего этапа разработки) |

**Порядок обработчиков в файле важен:** конкретные команды (`Command("start")` и т.д.) должны быть объявлены **до** общего `@router.message()` без фильтра — иначе echo-обработчик перехватит все сообщения раньше, чем до них дойдёт очередь команд.

**На будущее (за рамками текущего MVP):** здесь же будет добавляться функциональность онбординга (добавление тем/источников через диалог с ботом), когда дойдёт очередь до этой фичи из backlog.

## 12. `main.py` — точка входа и оркестрация

**Функция `send_digest_for_user(bot, provider, user_id)`** — весь пайплайн для одного пользователя:
1. Получить пользователя, проверить `is_paused`.
2. Забрать `chat_id` в переменную сразу (см. раздел 4 про `DetachedInstanceError`).
3. Для каждой активной темы: собрать статьи со всех источников (с `try/except` на каждый источник — сбой одного источника не должен обрушивать обработку остальных), продедуплицировать, вызвать ИИ, отправить сообщение (с разбиением на части при необходимости), пометить как отправленные.

**Обработка ошибок источников:** `try/except Exception` вокруг `fetch_articles` внутри цикла — реальный кейс из разработки: один источник (`consultant.ru/rss/hotdocs.xml`) периодически возвращал `IncompleteRead`/обрыв соединения, что без этой защиты роняло всю обработку остальных тем.

**Функция `main()`** — инициализация бота, планировщика (с `job_func = partial(send_digest_for_user, bot, provider)`), запуск polling. `try/finally` гарантирует остановку планировщика даже при сбое polling.

## 13. `scripts/seed_data.py`

**Назначение:** первоначальное и повторное заполнение БД темами/источниками — реализация "ручного онбординга" до появления полноценного диалогового онбординга в боте.

**Логика "найти или создать" для пользователя** — защита от `IntegrityError` при повторном запуске (если пользователь уже существует, например, уже писал боту `/start`).

**При добавлении новой темы:** дописать новый элемент в список `topics_data` и повторно запустить скрипт — существующие темы и источники не дублируются повторным запуском **только если** вы не меняете уже добавленные темы (скрипт в текущем виде не проверяет дубликаты тем — при повторном запуске с теми же данными темы будут созданы заново). Для аккуратного добавления одной новой темы без риска задвоения существующих — рекомендуется писать отдельный небольшой скрипт-разовик по аналогии, а не запускать `seed_data.py` целиком повторно.

## 14. Миграции (`migrations/`, `alembic.ini`)

**Ключевая настройка:** `migrations/env.py` переопределяет `sqlalchemy.url` программно, беря путь из `settings.db_path`:
```python
config.set_main_option("sqlalchemy.url", f"sqlite:///{settings.db_path}")
```
Это гарантирует, что `alembic` и основное приложение всегда работают с одним и тем же файлом БД — рассинхронизация путей уже становилась причиной реальной ошибки в проде (`no such table`).

**Как добавить новую миграцию при изменении `models.py`:**
```bash
alembic revision --autogenerate -m "краткое описание изменения"
alembic upgrade head
```
Обязательно проверяйте сгенерированный файл в `migrations/versions/` перед применением — автогенерация не всегда идеально угадывает намерение (особенно при переименовании полей).

**На сервере после `git pull` с новой миграцией:**
```bash
docker exec news-bot alembic upgrade head
```
(либо пересобрать и перезапустить контейнер — `CMD` в `Dockerfile` и так выполняет `alembic upgrade head` при каждом старте).

## 15. Тесты (`tests/`)

| Файл | Что проверяет |
|---|---|
| `test_db.py` | Дедупликация, включая изоляцию по `user_topic_id` |
| `test_digest_builder.py` | Разбиение длинных сообщений, форматирование |
| `test_ai_processor.py` | Формирование промпта (наличие темы, статей, требования про русский язык) — не качество ответа реальной модели |
| `test_news_fetcher.py` | Устойчивость к сетевым сбоям, пустым/битым RSS-лентам |

**Принцип тестирования ИИ-логики:** тесты не проверяют, "насколько умно" ответил ИИ (это не поддаётся детерминированной проверке) — только то, что промпт формируется корректно и что код правильно обрабатывает ответ провайдера. Реальное качество ответов проверяется вручную, периодически, на реальных данных.

**Перед любым рефакторингом — прогонять `pytest` полностью:**
```bash
pytest
```

## 16. Регламент типового сопровождения

### Посмотреть, что происходит с ботом прямо сейчас
```bash
docker ps
docker logs -f news-bot
```

### Перезапустить бота (например, после ручного вмешательства в БД)
```bash
docker restart news-bot
```

### Обновить код после изменений в репозитории
```bash
cd ~/news-bot
git pull
docker stop news-bot && docker rm news-bot
docker build -t news-bot .
docker run -d --name news-bot --env-file .env -v news-bot-data:/app/data --restart unless-stopped news-bot
```

### Добавить новую тему/источник
1. Отредактировать/дописать в `scripts/seed_data.py` (или написать отдельный точечный скрипт).
2. Выполнить внутри контейнера: `docker exec -it news-bot python scripts/seed_data.py`.
3. Перезапуск бота не обязателен для новых тем (они читаются из БД при каждом срабатывании расписания) — но обязателен, если менялось само расписание (`Schedule`), так как `setup_scheduler()` читает его только при старте.

### Проверить и восстановить бэкап
```bash
ls -la /root/backups
cp /root/backups/backup_ГГГГ-ММ-ДД_ЧЧ-ММ-СС.db /var/lib/docker/volumes/news-bot-data/_data/news_bot.db
docker restart news-bot
```

### Обновить зависимости
```bash
pip list --outdated
```
Обновлять по одной, перепроверяя `pytest` после каждой — не обновлять всё разом пакетом, чтобы легче было найти причину, если что-то сломается.

### Проверить лимиты внешних API
- Anthropic — баланс и лимиты в console.anthropic.com, раздел Billing.
- RSS-источники обычно без формальных лимитов, но при подозрении на блокировку — проверить вручную через `fetch_articles` в интерактивном режиме.

| Дайджест не приходит вообще, хотя бот отвечает на команды | В таблице `schedules` нет ни одной записи (например, расписание создавалось только локально для тестов, но не на сервере при деплое) | Проверить `docker exec -it news-bot python -c "..."` (запрос к `Schedule`, см. раздел 16); создать реальную запись расписания и **перезапустить контейнер** — `setup_scheduler()` читает расписания только при старте |
|---|---|---|
| `ModuleNotFoundError: No module named 'bot'` при запуске скрипта из подпапки | Python ищет модули относительно папки запускаемого файла | Добавить корень проекта в `sys.path` (см. `scripts/seed_data.py`) |
| `IntegrityError: UNIQUE constraint failed: users.telegram_chat_id` | Попытка создать уже существующего пользователя | Использовать паттерн "найти или создать" (`select` перед `insert`) |
| `ConflictingIdError` в APScheduler | Два расписания с одинаковым сгенерированным `id` | `id` задачи должен строиться по `schedule.id`, не по `user_id` |
| `DetachedInstanceError` | Обращение к полю ORM-объекта после закрытия/коммита сессии | Скопировать нужное значение в переменную заранее |
| `Bad Request: message is too long` (Telegram) | Сообщение длиннее 4096 символов | Отправлять по одному сообщению на тему + `split_into_messages` для подстраховки |
| `IncompleteRead` / обрыв соединения при сборе RSS | Нестабильность конкретного сервера или отсутствие `User-Agent` | `requests` с `timeout` и кастомным `User-Agent`, `try/except` вокруг каждого источника |
| `sqlite3.OperationalError: no such table` в контейнере | `alembic` и приложение используют разные файлы БД | Синхронизировать путь через `settings.db_path` в `migrations/env.py` |
| `anthropic.BadRequestError: credit balance is too low` | Не пополнен баланс Anthropic API | Пополнить баланс в console.anthropic.com → Billing |
| Запросы к Anthropic API не проходят с сервера в России | Региональное ограничение по IP, не только по оплате | Размещать сервер в поддерживаемом регионе, либо использовать VPN на сервере, либо перейти на локальную модель |
| `Fatal error in launcher` у `alembic.exe` после переноса `venv` | `venv` содержит абсолютные пути к старому расположению | Не переносить `venv` физически — пересоздавать заново на новом месте |
| Долгое "зависание" `pip install` / `python` на Windows | Антивирус в реальном времени сканирует каждый файл при импорте | Добавить папку проекта в исключения антивируса |
